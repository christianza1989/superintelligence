## Observed source-planning failure

B automatically called status, search, five inspections, two public discovery submissions and one reviewed-source selection submission. The local calls succeeded. The three submissions supplied deadlines hours away, exceeding the application's existing 120-second client bound. They failed before HTTP submission. The public error boundary returned a generic error, so the host could not identify the deadline problem and stopped without a Jev recommendation.

The isolated backend had zero jobs, artifacts, budget reservations and usage records; its dispatch audit also recorded zero model dispatches. The cumulative USD 3 ledger remained at USD 0.30 held across its three earlier invocations. This was not a Jev abstention or a judgment on GitHub candidate quality. Joint native GitHub/Jev planning failed before submission; full-chain value is unproven. Original plans, raw transcripts, hashes, failure responses and read-only backend counts are preserved privately. Grants were revoked, API/worker stopped, and only the owned PostgreSQL fixture was stopped.

## Repair after the frozen pair

Source 0.10.1 / schema 1.11.1 makes deadlines optional on `zero_discover`, `zero_select` and `zero_source`: the server supplies a deadline from its clock within the unchanged transport bound. Explicit expired or distant deadlines fail before dispatch with a fixed, bounded instruction to omit/correct the field. No input, private error or path is reflected. Replaying the same keyed source request with a fresh transport deadline retains the original signed deadline, job and digest; it cannot extend work or pay twice. Changed request content still conflicts. Other execution profiles retain their existing controls; backend authorization and budget checks are unchanged.

The four affected transport/client suites passed 84 tests; adapter TypeScript passed. Tests exercise omitted deadlines for all three tools, explicit expired/distant deadlines, no submission on rejection, error redaction and the real STDIO launcher. All 35 API/PostgreSQL/Graphile controls passed without skips using offline GitHub/Jev boundaries, including source replay across reconnect with the original deadline and exactly one dispatch. Linux package planning/STDIO/HTTP controls and Windows portable discovery/planning controls passed. The first 0.10.1 package check failed because the compatibility manifests still declared 0.10.0; that package is retained, all three source manifests were corrected, and a newly generated package passed. This repair was made after capture/closure, never inside the frozen pair. It is not yet a new native pair or a joint live GitHub/Jev qualification.

## Whole-task comparison

Planning overhead can be a useful investment, but its return remains a hypothesis. Record planning/research, coding/integration, verification/repairs and the total to the same independently checked quality threshold. Include Jev/provider costs and failed attempts; keep the human review pause separate from active work. A better plan may improve correctness or reduce later repairs without reducing planning time. Conversely, a richer or more expensive plan is not evidence of better code.

Review both complete plans before application generation, as requested. A subsequent repair trial needs new clean chats and a new freeze. Do not combine 0.10.0 failure results with repaired results, change a prompt/checker inside a cohort, or close MVP/repeated-benefit gates from this development pair.
