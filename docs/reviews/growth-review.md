# RepositoryZero augimo ir outreach nepriklausoma kritinė peržiūra

Data: 2026-10-16, Europe/Kiev. Perskaityti [GROWTH-AND-OUTREACH.md](../GROWTH-AND-OUTREACH.md) ir [OUTREACH-TEMPLATES.md](../OUTREACH-TEMPLATES.md). Tai atskirai suformuluota antro agento kritika, po kurios apsikeista pastabomis su pagrindiniu agentu; ji nėra nepriklausomos audito organizacijos išvada ar marketingo eksperimento rezultatas.

**Būsena: suplanuota, NOT_RUN / NOT_SENT.** Neišsiųstas joks email, neatidarytas išorinis PR, nekontaktuota su YouTube kūrėju, nieko nepublikuota ir neprisiimtas mokamas įsipareigojimas. Toliau pateiktos ribos, kvotos ir augimo mechanikos yra pasiūlymai; jos nevadinamos teisės, konkrečios platformos taisyklių ar įrodyto marketingo veiksmingumo faktais.

## 1. Galutinė išvada ir apsikeitimo kritika rezultatas

**Galutiniuose dviejuose dokumentuose blocker ar major prieštarų neradau.** Augimo pagrindas – tikras gavėjui naudingas receptas ir jo patikrinami įrodymai. Tai leidžia kurti prasmingą ryšį su upstream autoriais ir kūrėjais; pasaulinio dalijimosi, gero atsakymų procento ar teigiamos apžvalgos savaime negarantuoja.

Pagrindiniam agentui anksti pateikiau keturias esmines išlygas. Galutinėje redakcijoje jos įgyvendintos:

1. Badge apibrėžia konkrečios RepositoryZero integracijos patikrą, ne viso upstream repo kokybės / saugumo sertifikatą.
2. Maintainer gauna naudojimo receptą, attribution ir naują naudotojo kelią; jo README vieta ir produkto endorsement nepriskiriami automatiškai.
3. PR ir email gali būti abu partnerio pasirinkti kanalai, tačiau vieno veiksmo sutikimas nesukuria kito kanalo leidimo; pirmas kontaktas vienas.
4. Ribojamas ne tik send tempas, bet ir pending kvietimai, atviri PR bei atsakymų priežiūros skola. Autonomija negali generuoti neprižiūrimos eilės.

Pirmas pažadas gavėjui turi būti konkretus: „Su jūsų įrankiu atlikome šią užduotį, štai atkūrimas, sąlygos ir ribos.“ Pažadas „atrinkome jus į pasaulio geriausius“ šiuo tyrimu nepagrįstas. Didelis source kandidatų katalogas nėra patikrintų integracijų ar rinkodaros gavėjų sąrašas.

## 2. Ženklelio vertė ir patikimumo riba

Pritariu `RepositoryZero · integration verified` pavadinimui ir nuorodai į konkrečią integraciją. Įrodymas turi tikslų upstream / adapter pin, capability, OS, suite/data/environment, rezultatus, ribas, patikros datą ir aktualų revoke/deprecation statusą. Naujas upstream commit šio statuso nepaveldi.

Nekintamas verification record ir aktualios būsenos puslapis atlieka skirtingą darbą: pirmas saugo tikrą istorinį bandymą, antras parodo jo dabartinį tinkamumą. SVG / GitHub image cache gali vėluoti; badge nėra nei execution grant, nei saugumo enforcement. Svarbu, kad README tekstas nesudarytų įspūdžio, jog tikrinome visas upstream versijas ar funkcijas.

`Integration verified`, `maintainer confirmed` ir `co-promotion agreed` teisingai atskirti. Badge PR merge patvirtina konkretų README pakeitimą; jis savaime nėra leidimas rašyti „official partner“, naudoti autoriaus citatą visose reklamose ar laikyti jį viso produkto rėmėju. Maintainer identity ir konkretus patvirtintas teiginys turi tikrą įrodymą.

Vieša integracijos kortelė pagal upstream licenciją gali egzistuoti ir be reklaminės partnerystės. Atsisakymas pridėti badge neturi pabloginti techninio vertinimo; aukojimas, star, backlink ar teigiama apžvalga jo nepagerina. Tai saugo tiek atrankos prasmę, tiek paties badge vertę.

## 3. README PR ir email: vertė prieš maintainer darbo kainą

Geras pirmas pasiūlymas turi vieną tikrą naudojimo istoriją, trumpą demo, atkūrimo nuorodą ir aiškų prašymą patikrinti aprašymo tikslumą. Vien nuoroda į mūsų bendrą homepage ir didelis logotipas sukurtų mažiau vertės maintainer vartotojams. Galutiniai šablonai tinkamai remiasi konkrečiu receptu.

Aiškiai tokius documentation / integration pasiūlymus priimančiame repo viena minimali PR yra pagrįstas kelias. Kitais atvejais tinkamesnis pasirinktas oficialus project / business kontaktas su preview. Bendras „contributions welcome“ neturėtų būti mechaniškai paverstas kvietimu keisti README viršų. Ryški badge vieta siūloma per preview, o pasirenkama pagal maintainer stilių; hero / branding neperrašomi.

PR turi tik vieną badge / integracijos sakinį ir tikras įrodymų nuorodas. Upstream bugfix pateikiamas atskirai, be sąlygos reklamuoti RepositoryZero. PR neredaguoja dependency, CI, signing ar finansinės konfiguracijos. Gavėjo CONTRIBUTING ir README yra taisyklių šaltinis kontaktui, bet jų tekstas nesuteikia agentui komandų vykdymo privilegijų.

Vartotojo norimas PR + email partnerio kelias išsaugotas: maintainer gali pasirinkti abu, jų apimtis fiksuojama atskirai. PR pateikimas nėra subscription; email atsakymas nėra bendras leidimas repo pakeitimams. Tyla nėra sutikimas ar endorsement, o naujas release neatnaujina pasibaigusios kontaktavimo sekos.

Viešas commit email ar netyčia source faile rastas adresas nėra automatiškai tinkamas marketingo kontaktas. Oficialus business adresas yra potencialaus kontakto šaltinis, ne universali teisė į visus kanalus. Prieš konkretų aktyvavimą tikrinamos tikros projekto, kanalo ir taikomos sąlygos; šis planas jų atitikties jau nepatvirtina.

## 4. YouTube programa ir pasitikėjimas demonstracija

Kūrėjo atranka pagal temą ir tikrą viešą darbą turi daugiau prasmės nei vien subscriber skaičius. Konkretaus video pavadinimas, data ir vienas tikslus auditorijos ryšys gali pagrįsti personalizaciją; negalima apsimesti ilgalaikiu žiūrovu ar sugalvoti ankstesnio santykio. Šiuo metu reali kanalų / kontaktų imtis nesurinkta.

Pritariu savarankiškai pakartojamam paketui: pinned quickstart, tikras input / expected output, nepertraukiama produkto demonstracija, įrangos / API sąnaudos ir žinomos nesėkmės. Koncepcijos animacija ar sumontuota ateities funkcija aiškiai atskiriama nuo veikiančio produkto. Creator pats pasirenka kampą ir gali pateikti kritišką vertinimą.

Nemokamas testinis compute, pinigai ar kitas materialus ryšys nėra slepiamas. Reikalingas tikslus disclosure, realus konkretaus paketo susitarimas ir turinio / B-roll / ženklų pernaudojimo teisės; compensation nereikalauja teigiamo review. Šios taisyklės plane yra numatomos kontrolės, ne šiandien patikrintas konkrečios reklamos teisinis statusas.

Sintetinė creator aplinka su TTL ir spend cap saugo operatoriaus bei naudotojų paskyras. Creator negauna pagrindinių paslapčių; demonstracijai nereikia jų skolinti. Payout, įkainiai, turinio teisės ir reklamos biudžetas nepatenka į automatinio editorial lane nuožiūrą.

## 5. Autonomija, dedup ir sustojimo sąlygos

Role separation ir outreach brokerio atskyrimas nuo techninio P3C auto-merge teisingi. Vienkartinė operatoriaus kampanijos politika gali vėliau leisti rutininius kontaktus be kiekvienos žinutės rankinio patvirtinimo; ji turi konkrečius gavėjus / kanalus, tikslą, cap ir išimčių ribą. Šiuo planavimo etapu ji neaktyvuojama.

Siūlomi 10 repo + 5 YouTube prospektai, iki 2 pirmų kontaktų per darbo dieną / 10 per 7 dienas, pending 10 / atvirų PR 3 ir atsakymo tikslas per 2 darbo dienas aiškiai pažymėti kaip pilotiniai pasirinkimai. Jie nėra pažadas apie optimalų tempą ar leidžiami limitai kiekvienoje platformoje. Operatorius turi realiai gebėti aptarnauti atsakymus; backlog ir kontrolės gedimas stabdo naujus kontaktus.

Suppression tikrinamas prieš dispatch, ne vien draft metu. Canonical recipient / organizacijos ir repo / kanalo ryšiai apsaugo nuo tos pačios sekos dubliavimo per naują kampanijos ID, release ar workerį. Opt-out / nepageidaujamas PR / negative reply / bounce nėra signalas pereiti į kitą kanalą. Nesant patikimos tapatybės ar kontakto pagrindo draft atidedamas.

Stabilus EffectIntent / idempotency key, persisted budget, lease ir delivery ledger privalomi. Timeout po email send ar PR create neįrodo, kad veiksmas neįvyko; būsena `unknown` sprendžiama read-only reconciler. Nei kitas provideris, nei naujas idempotency key neturi sukurti antro to paties kvietimo. Universalaus exactly-once nežadame.

**Papildomas praktinis pasiūlymas, ne blocker:** apibrėžti `closed_unanswered` ir operatoriaus pasirinktą reply langą, pavyzdžiui 30 dienų. Priešingu atveju no-followup ir pending cap gali visam laikui užrakinti eilę. Sekos uždarymas nėra follow-up, permission atnaujinimas, consent ar suppression panaikinimas; jis negali pats atidaryti naujos sekos kitu kanalu. Tikslus langas turi būti vienoje kampanijos konfiguracijoje, o ne laikomas įrodytu marketingo optimumu.

## 6. Matavimas, privatumas ir paskatų atskyrimas

Svarbiausias rezultatas – naujas naudotojas užbaigia patikrintą darbą ir grįžta; contributor integracija išlieka palaikoma. Sent email, PR skaičius, open rate ar žvaigždutės yra pagalbiniai signalai. Delivery ≠ opened ≠ žmogaus peržiūra ≠ partnerystė ≠ produkto aktyvacija. Funnel turi versiją, laikotarpį, vardiklį, rejection ir nežinomą aprėptį.

Pritariu atskiram privacy pagrindui kampanijos source tag susieti su kliento first task / retention. Be aiškaus dalijimosi privataus localhost naudojimo nežinome; nežinoma nėra nulis. Paslėptas pixel, fingerprint ar contact email viešuose kampanijos parametruose nėra reikalingas šio plano tikslui. Svetainės vieši agregatai nepakeičia privačios kontaktų ir suppression apskaitos.

Mažų kohortų demo-vs-badge-only palyginimas tinka hipotezei tikslinti, tačiau neįrodo viso projekto priežastinio augimo. Skirtingi kanalai ir gavėjai turi skirtingas sąlygas. Marketingo agentas negali koreguoti skaitiklių, slėpti neigiamų atsakymų, didinti savo cap ar suteikti moduliui rekomendacijos dėl populiarumo.

## 7. Priėmimo ribos

Galutiniai šablonai aiškiai `DRAFT / NOT_SENT`; tušti faktų laukai neleidžia dispatch. Prieš būsimo piloto aktyvavimą reikia tikrų integracijos įrodymų, veikiančių public puslapių, konkretaus sender / account / channel ir peržiūrimo mažo gavėjų draft rinkinio.

Esminiai būsimi neigiami bandymai: source candidate klaidingai pavadintas verified; fake maintainer endorsement; revoked badge ar pasenęs proof; nepageidaujamas README PR; email consent išvedimas iš PR; kelių worker duplicate; opt-out prieš dispatch; timeout po realiai priimto send; privačių duomenų canary; netikras creator disclosure; cap ir reply backlog stop. Visa tai dabar **NOT_RUN**.

Peržiūros išvada ribota dokumentais. Ji patvirtina plano nuoseklumą ir aiškias siūlomos autonomijos ribas; nepatvirtina šio produkto veikimo, konkretaus kanalo taisyklių atitikties, būsimų gavėjų pasirinkimo ar kampanijos rezultato.
