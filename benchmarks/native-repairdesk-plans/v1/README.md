# RepairDesk: native plan-only pilot

This is a more complex planning task, not a working-application benchmark. It covers linked customer/device/repair workflows, stock transactions, CSV import, PDF output, local roles, attachments and ZIP backup/restore.

Both fresh native chats receive the same [request](prompt.txt) and [specification](SPEC.md), with the same model and effort. Neither user prompt hints at source search, GitHub or Zero. Ordinary libraries are permitted. A has no Zero metadata, skills or project guidance. B's installed skill, discovery MCP and operator-selected generic project guidance are disclosed and pinned before either turn. Native host/provider caches are uncontrolled. Run the two chats sequentially in a predeclared order and retain the full transcripts, failures and non-use.

Read-only discovery is allowed during planning. No package installs, application source writes, application execution, prepare/verify jobs or paid model calls belong to this stage. Stop for human review before implementation.

Review the plans qualitatively against the same public requirements: workflow coverage, architecture and data integrity, authorization, backup safety, concrete source evidence, module limits and integration gaps, failure/recovery and meaningful validation. Do not invent a numerical quality score after reading the plans, infer implementation quality from prose, or claim repeated benefit from one pair. A discovered source, a proposed dependency, scoped prepared-module compatibility, and actual integration are separate facts. Preserve an honest no-fit or extension requirement, including a component that covers archive creation but not restore.
