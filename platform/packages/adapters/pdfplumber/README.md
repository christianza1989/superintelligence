# Explicit lightweight born-digital table candidate

This is a separate frozen candidate epoch, not a fallback from the rejected Docling profile. It uses pdfplumber 0.11.10 at release source `7d4f2f582f2d99f9e60ba522fdf7afd2f6d54c62`, eight exact binary wheel hashes, no ML weights and no OCR. RepositoryZero discovery returned a source-only candidate with license approval and runtime qualification still false; the local runtime evidence below is separate from that catalog.

The supported scope is rectangular ruled tables in born-digital PDFs. Both table strategies are `lines`, with fixed three-point snapping/join/intersection tolerances. Missing or merged grid-cell geometry is unsupported. No text-strategy fallback, schema guessing, model, shell code or external service is used. Cell text, grid offsets and page/bounding-box provenance come from the parser's actual objects. The unchanged independent grader remains in the frozen Docling experiment namespace; expected numeric values were committed before either candidate ran.

Explicit preparation is `node platform/scripts/zero-pdfplumber-prepare.mjs --prepare`; the spike is `node platform/scripts/zero-pdfplumber-spike.mjs --run`. Both entry points deny default/wrong flags without Docker or downloads. The two fixed PDF experiments share a small wheel-download/image/fixture harness; it accepts only their names and creates no scheduler, application API or general integration framework.

Limits: archives <=64 MiB, models zero, installed image plus retained cache <=512 MiB, prepare <=180 seconds per attempt. Runtime is network-none, read-only, two CPU quota/compute threads, 512 MiB without swap, 30 seconds per file, input <=1 MiB and five pages, output <=1 MiB. An external watchdog kills only the owned container and requires confirmed cleanup before success. Runtime data are only the ten synthetic fixtures. Normal application imports, discovery and settings activate nothing.

The actual sealed run passed ten of ten fixtures, all 56 numeric cells, eleven tables, eleven pages and page/bounding-box checks. Suite time was 998 ms; first file 232 ms; separate warm repetition 8 ms. Process peak RSS was 41,152,512 bytes. No OOM occurred; the owned container was removed; paid model calls were zero. These are controlled synthetic development results, not independent holdout accuracy, arbitrary PDF support or repeated user benefit. Docling's preparation failures are not a model quality comparator.

The installed image is 310,032,256 bytes, including the shared Python base 206,918,255 bytes and a dependency delta 103,114,001 bytes. Wheel archives total 22,884,554 bytes; models zero. The conservative retained upper bound is 356,908,499 bytes, including owned preparation cache, rounded-up private BuildKit sizes and a one-MiB report reserve. BuildKit can reuse mutable record IDs; the initial incomplete accounting attempt was invalidated and the corrected case has a regression. Physical filesystem deduplication was not measured. This component size does not prove the whole active Zero/browser/PDF/coding profile meets G0 <=2,000,000,000 bytes.

Preparation is experimental: the final retained footprint and payload caps are measured, but peak filesystem quotas and cancellation of daemon-side BuildKit work after a CLI timeout are not proven. Automatic/default preparation, durable Graphile/ArtifactRef ownership, authenticated application exposure, independent holdout, transitive redistribution review and full G0/G1 acceptance remain open. The worker acceptance gate is not satisfied by this fixture script.

See the [redacted measured report](spike-results-2026-10-17.json), [frozen profile](profile.json) and [wheel lock](wheels.lock.json). Local ignored caches and optional images retain experiment evidence; they are not silently included in the default product installation.
